💬 Support & Contributing

Sunk Cost is a free, independent, one-person project — support happens in the open, on GitHub.

Found a bug, or have a question?

Post a GitHub Issue — it's the one place bugs, questions, and feature ideas all get tracked, and it's free and doesn't require anything but a GitHub account (also free) to post.

→ Open a new issue
github.com/lisajill/sunk-cost/issues/new

When reporting a bug, it helps a lot to include:

  • What you were doing right before it happened
  • What you expected vs. what actually happened
  • A screenshot, if it's something visual

Before posting, it's worth a quick look through existing issues in case someone's already reported the same thing.

Want to contribute code?

Contributions are welcome. Sunk Cost is a plain Swift Package — no Xcode project to fight with, just the Swift toolchain that ships with Xcode.

git clone https://github.com/lisajill/sunk-cost.git
cd sunk-cost
swift test                    # run the test suite
./AppPackaging/build_app.sh   # build and package Sunk Cost.app

Before diving into the code, read CLAUDE.md in the repo root — it covers the architecture, a handful of non-obvious gotchas that have already been hit once (so you don't have to hit them again), and the reasoning behind some deliberate design choices (like why there's no network code anywhere, on purpose).

Sending a pull request

The main branch requires changes to come in through a pull request rather than a direct push, so:

  1. Fork the repo, or create a branch if you have write access
  2. Make your change, with tests if it touches SunkCostCore (the testable logic layer — see CLAUDE.md's architecture section for what belongs there vs. the SwiftUI layer)
  3. Run swift test and make sure everything still passes
  4. Open a pull request against main describing what changed and why

Small, focused PRs are easier to review than big ones — if you're thinking about a large change, opening an issue first to talk it through is a good idea before writing a lot of code.

New to the codebase? The project's own commit history is a genuinely good way to see the reasoning behind past decisions — commit messages here consistently explain why, not just what.
